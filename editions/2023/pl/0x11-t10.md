# OWASP Top 10 ryzyk bezpieczeństwa API – 2023

| Ryzyko | Opis |
| ---- | ----------- |
| [API1:2023 - Niepoprawna autoryzacja na poziomie obiektu][api1] | API zwykle udostępniają endpointy obsługujące identyfikatory obiektów, co tworzy rozległą powierzchnię ataku związaną z problemami kontroli dostępu na poziomie obiektu. Kontrole autoryzacji na poziomie obiektu należy uwzględnić w każdej funkcji, która uzyskuje dostęp do źródła danych przy użyciu identyfikatora pochodzącego od użytkownika. |
| [API2:2023 - Niepoprawne uwierzytelnianie][api2] | Mechanizmy uwierzytelniania są często implementowane nieprawidłowo, co pozwala atakującym przejmować tokeny uwierzytelniające lub wykorzystywać błędy implementacji, aby tymczasowo lub trwale podszywać się pod innych użytkowników. Naruszenie zdolności systemu do identyfikacji klienta/użytkownika narusza bezpieczeństwo API jako całości. |
| [API3:2023 - Niepoprawna autoryzacja na poziomie właściwości obiektu][api3] | Ta kategoria łączy [API3:2019 Nadmierne ujawnianie danych (Excessive Data Exposure)][1] i [API6:2019 - Mass Assignment][2], koncentrując się na przyczynie źródłowej: braku lub niewłaściwej walidacji autoryzacji na poziomie właściwości obiektu. Prowadzi to do ujawnienia informacji lub manipulowania nimi przez nieuprawnione strony. |
| [API4:2023 - Nieograniczona konsumpcja zasobów][api4] | Obsługa żądań API wymaga zasobów, takich jak przepustowość sieci, CPU, pamięć i przestrzeń dyskowa. Inne zasoby, takie jak e-maile/SMS-y/połączenia telefoniczne czy weryfikacja biometryczna, są udostępniane przez dostawców usług poprzez integracje API i opłacane za każde żądanie. Udane ataki mogą prowadzić do odmowy usługi (Denial of Service) lub wzrostu kosztów operacyjnych. |
| [API5:2023 - Niepoprawna autoryzacja na poziomie funkcji][api5] | Złożone polityki kontroli dostępu z różnymi hierarchiami, grupami i rolami oraz niejasny podział między funkcjami administracyjnymi a zwykłymi prowadzą zwykle do błędów autoryzacji. Wykorzystując te problemy, atakujący mogą uzyskać dostęp do zasobów innych użytkowników i/lub funkcji administracyjnych. |
| [API6:2023 - Nieograniczony dostęp do wrażliwych przepływów biznesowych][api6] | API podatne na to ryzyko udostępniają przepływ biznesowy, taki jak zakup biletu czy opublikowanie komentarza, nie uwzględniając tego, jak ta funkcjonalność mogłaby zaszkodzić firmie, gdyby była nadmiernie wykorzystywana w sposób zautomatyzowany. Nie musi to wynikać z błędów implementacji. |
| [API7:2023 - Server Side Request Forgery][api7] | Błędy typu Server-Side Request Forgery (SSRF) mogą wystąpić, gdy API pobiera zdalny zasób bez walidacji URI dostarczonego przez użytkownika. Umożliwia to atakującemu zmuszenie aplikacji do wysłania spreparowanego żądania do nieoczekiwanego miejsca docelowego, nawet jeśli jest ono chronione przez zaporę sieciową lub VPN. |
| [API8:2023 - Błędna konfiguracja zabezpieczeń][api8] | API i wspierające je systemy zwykle zawierają złożone konfiguracje, których celem jest zwiększenie możliwości dostosowania API. Inżynierowie oprogramowania i DevOps mogą przeoczyć te konfiguracje lub nie stosować najlepszych praktyk bezpieczeństwa w zakresie konfiguracji, otwierając drogę do różnego rodzaju ataków. |
| [API9:2023 - Niewłaściwe zarządzanie inwentarzem][api9] | API zwykle udostępniają więcej endpointów niż tradycyjne aplikacje webowe, dlatego właściwa i aktualna dokumentacja ma ogromne znaczenie. Właściwy inwentarz hostów i wdrożonych wersji API jest również ważny, aby ograniczać problemy takie jak przestarzałe wersje API i udostępnione endpointy debugowania. |
| [API10:2023 - Niebezpieczna konsumpcja API][api10] | Programiści zwykle bardziej ufają danym otrzymanym z API stron trzecich niż danym wejściowym od użytkowników, dlatego stosują słabsze standardy bezpieczeństwa. Aby skompromitować API, atakujący biorą na cel zintegrowane usługi stron trzecich, zamiast próbować bezpośrednio skompromitować docelowe API. |
